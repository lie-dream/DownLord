# DownLord Connector（浏览器扩展）

DownLord 的**第二个可分发工件**：一个 MV3 浏览器扩展，随 DownLord 安装包一起分发，与主程序分开构建、分开安装。

> **v0.4 已交付的全部能力**：**下载接管**（浏览器里点下载 → DownLord 接住，**弹确认框、永不静默**）、**网页媒体嗅探**（**默认关闭**，在 popup 里自己开）、**取 Cookie**（需要登录态时由 **DownLord 点名、扩展给予**，用完即删）。
> ⚠️ **扩展需要你手动加载，没有一键安装、也没有强制流程** —— 它**未上任何扩展商店**、**不打 `.crx`**，只能开**开发人员模式**、自己选目录加载（见下方「安装」）。
> ⚠️ **「从扩展获取 Cookie」这一档只对扩展点过名的域生效** —— 你绕开扩展、**直接把 URL 粘进 DownLord**，而此前又从没经扩展借过这个站，这一档**取不到 Cookie**，下载会如实报「需要登录」。这不是 bug，也**不是任何设计能堵上的**：通道**不做反向推送**，DownLord 无法主动向浏览器索取，只能在扩展先来说话时于应答里点名（见下方「安全边界」与「已知边界」第 ④ 条）。要用这一档，**请从扩展这一侧发起下载**。

---

## ★ 诚实边界（浏览器支持范围）

- **Edge** —— 已实测通过，承诺范围内。
- **Chrome** —— 已实测通过，承诺范围内（v1.0 Task 2 在 Edge / Chrome 双端各跑一遍全链）。
- **Firefox** —— **本版不做**。Firefox 是不同引擎（`browser.*` 命名空间、MV3 background 用**事件页**而非 service worker、正式版**强制扩展签名**导致分发路径不同），需要单独验证。适配层已留口，但**未验证 ≠ 可用**。
- 上述结论基于 **Edge + Chrome 双浏览器实测**，**不得据此宣称全部 Chromium 浏览器已验证** —— Brave / Chromium / Opera / Vivaldi 本版未实测。

## 第 0 步：先在 DownLord 里启用本地通道

⚠️ **这一步必须在装扩展之前（或至少在配对之前）做完** —— 扩展只是这条通道的客户端，通道没开，装好也连不上。

1. 打开 DownLord →「**设置 → 浏览器扩展**」；
2. 打开「**启用本地通道**」开关（**默认是关的** —— 不装扩展的用户不该白开一个监听端口）；
3. 第一行状态应变成 `监听中 · 127.0.0.1:52330`。
   - 若显示 `端口 52330 被占用，通道未启动`：改个端口（如 `52340`）→ 点「重新绑定」→ **记住这个数字**，配对时要填。
   - DownLord **不会自动顺延到 52331、也不扫描端口** —— 顺延会让「配对一次长期有效」失去意义，故被占就如实不启动。
4. 同一分组里能看到**配对码**（默认遮蔽，点「显示」可看，点「复制」拿走）和**扩展在本机的绝对路径**（下一步要用）。

## 安装（旁加载 · 两条路径）

### 路径 A — 用安装态产物（面向普通用户）

1. 装好 DownLord；
2. 打开 `edge://extensions/`（Chrome 为 `chrome://extensions/`），右下角开**「开发人员模式」**；
3. 点**「加载解压缩的扩展」**，选目录：

   ```
   %LOCALAPPDATA%\Programs\DownLord\resources\extension
   ```

   （若安装时改过路径，则为 `<你选的安装目录>\resources\extension`；也可以直接用第 0 步里「复制路径」拿到的那一行 —— 那是从运行时算出来的真实路径，不是手抄的）
4. 扩展列表出现「DownLord Connector」、工具栏出现图标 → 装好了。

### 路径 B — 用仓库构建产物（面向开发者）

1. `npm install` → `npm run build`；
2. 同样在 `edge://extensions/`（Chrome 为 `chrome://extensions/`）开**开发人员模式** → **「加载解压缩的扩展」** → 选 `<仓库根>\extension\dist`。

### ⚠️ 不要选 `extension/` 源目录

只能选上面两个目录之一。**`extension/`（源码目录）不是可加载目录** —— 那里的 `manifest.json` 故意**不含 `version` 字段**（版本由构建脚本从 `package.json` 注入，避免手抄漂移），而 `version` 是 MV3 manifest 的必填字段；目录里也只有 `.ts` 源码，没有浏览器能执行的 `sw.js` / `popup.js`。

### zip 分发（可选）

`npm run build` 还会在仓库 `dist/` 下产出 `downlord-extension-<version>.zip`（zip 根就是 `manifest.json`，不套子目录）。解压后加载**解压出来的那个目录**即可，效果同路径 B。
（注：`npm run dev:extension` 的 watch 模式**不打 zip**，只刷新可加载解压目录。）

## 配对（一次，此后长期有效）

1. 点浏览器工具栏里的 DownLord 图标打开 popup；
2. **端口** —— 填第 0 步看到的那个数字（预填 `52330`，那个值取自共享契约，不是写死在 popup 里的魔法数）；
3. **配对码** —— 回 DownLord 点「复制」，粘进来。粘贴时带的首尾空格 / 换行会被自动去掉；但**大小写与长度不容忍**（它是 64 位小写十六进制）；
4. 点「**保存并连接**」→ popup 显示「已连接 DownLord（应用 vX）」；回 DownLord 设置页，第二行状态显示 `已连接`。

配对码存在 `chrome.storage.local`（**不是** `session`）—— 所以关浏览器、重启电脑都不用重新粘。代价是它**明文落在浏览器的配置目录里**，见下文「安全边界」。

### 端口与配对码是两件事

|  | 它是什么 | 改了要做什么 |
|---|---|---|
| **配对码** | 扩展的**身份** | 只在 DownLord 侧点「重新生成」时才变 —— **旧配对当场失效**，必须回 popup 重新粘一次 |
| **端口** | 只是**连接参数** | **不需要重新配对**；但扩展**读不了本机文件、不会自动跟上** —— DownLord 侧改成 N，就得回 popup 把端口也改成 N。DownLord 会弹一条提醒，并在端口栏下方**常驻一行**「当前生效:N」，过后回去也看得见 |

### 两侧各说各的 —— 别把两个「配对」读成同一件事

**DownLord 设置页第二行**显示的是**连接三态**（基于握手），**第三态不叫「断开」**：

| DownLord 设置页第二行 | 含义 |
|---|---|
| **未配对** | 本次启动以来一次都没收到过握手 |
| **已连接** | 最近 5 分钟内握手成功过 |
| **待活动** | 已配对，但这次启动以来一直没握手 —— **不是断开**。握手是**事件驱动**的（sw 冷启动 / 打开 popup / 有真实业务请求），**没有定期心跳**，所以「久没握手」既可能是扩展停了、也可能只是你一天没下载。分不清就不假装分得清 |

**popup 里那一行叫「配对码」，取值只有「已保存 / 未保存」** —— 它只回答「这台浏览器上存没存过那串码」，**不回答「配对成没成」**。

⚠️ **为什么不共用「已配对」这个词**：扩展**无从判断这串码对不对**（对不对只有 DownLord 说了算）。若这行也写「已配对」，你粘错一串格式合法的码时就会看到「连不上 DownLord」+「已配对」这种自相矛盾的组合。**配对成没成，看 popup 的结果行**，不看这一行。

## 看控制台

### service worker（后台）

1. `edge://extensions/` → 找到「DownLord Connector」卡片；
2. 点卡片上的**「服务工作进程」/「Service worker」**链接 → 打开 DevTools，`Console` 面板即 sw 的日志；
3. **状态显示「不活动 / inactive」是正常的** —— MV3 的 service worker 空闲即被浏览器销毁，这是常态而非故障。点一下链接、或触发一次事件（比如打开 popup）它就会醒。

### popup

在 popup 上**右键 → 「检查」**。popup 关闭即销毁，DevTools 也随之关闭 —— 想看 popup 的启动日志，得**先开着 DevTools 再重开 popup**。

## 改代码后怎么重载

| 改了什么 | 怎么生效 |
|---|---|
| 扩展的 TS / HTML | `npm run dev:extension`（watch，自动重 bundle）→ 回 `edge://extensions/` 点该卡片的**刷新（⟳）**按钮 |
| `manifest.json` | 同上，**必须**点刷新 —— manifest **不热更新** |
| 一次性构建 | `npm run build` 后同样点刷新 |
| DownLord 升级后扩展失效 | 见下文「已知边界」第 ① 条 |

### 「浏览器里跑的到底是哪一版」—— 看 popup 的**构建标记**

每次 `npm run build` 都会给 `sw.js` 与 `popup.js` 注入**同一个**构建标记（形如 `0.4.0+20260809-143022`，**带构建时刻**）。打开 popup：

- 诊断区「构建标记」那一行显示的是 **popup 自己那份**；
- 下面若出现「⚠ popup 与后台脚本版本不一致（popup … / 后台 …）」，说明浏览器跑的 `sw.js` **不是这次构建出来的那个** —— 到 `edge://extensions` 点该卡片的刷新（⟳）；
- **后台那份是 sw 自己报上来的**，不是从 manifest 读的。这是刻意的：浏览器缓存旧 SW 脚本时 manifest 是新的、`sw.js` 是旧的，读 manifest 会给出**错误的安心感**；
- ⚠️ **watch 模式（`npm run dev:extension`）下这个标记在一次 watch 会话内恒定**（esbuild 的 define 在建 context 时就固化了）。要拿到新标记，重启 watch 或跑一次 `npm run build`。

## 故障排查

### popup 上的四种提示 → 该做什么

| popup 提示 | 原因 / 怎么办 |
|---|---|
| **连不上 DownLord** | ① DownLord 是否在运行 ② 第 0 步那个开关是否还开着 ③ popup 里的端口是否与 DownLord 设置页显示的一致 |
| **配对码不被接受** | 回 DownLord 点「复制」配对码再粘一次（它可能被重新生成过；重新生成会让旧配对**立即**失效） |
| **协议版本不一致** | 升级较旧的那一边 —— 提示里会写明哪边旧。扩展与 DownLord 是一起分发的，出现这个通常意味着两边版本被手动混搭了 |
| **端口上的服务没有按 DownLord 协议应答** | 那个端口被**别的程序**占了 —— 在 DownLord 里换个端口，再回 popup 改成同一个数字。⚠️ 这也意味着**刚才那次尝试已经把配对码发给了那个程序**（见下文「安全边界」第 ⑤ 条） |

### 其它

| 现象 | 原因 / 怎么办 |
|---|---|
| 加载时报 manifest 错误 | 大概率选错了目录 —— 检查是不是选了 `extension/` 源目录（见上文 ⚠️）。正确目录里应有 `manifest.json` / `sw.js` / `popup.html` / `popup.js` / `icons/` 五件 |
| 路径 B 下 `extension/dist` 不存在 | 还没构建。先跑 `npm run build`（或 `npm run dev:extension`） |
| **sw 控制台是空的** | **这是正常的**。sw 只在出错时才 `console.error`，成功路径不打日志 —— 「空」= 没出错，**不是**「sw 没跑」。确认 sw 活着请看 popup 里的**唤醒计数**，别看控制台 |
| popup 显示的版本不对 | 版本从 `package.json` 注入。改了版本号要重新 `npm run build`，再点刷新 |
| 点了扩展的「重新加载」，popup 的唤醒计数**归零** | 不该发生 —— 计数落在 `chrome.storage`，跨重载应当**持续增长**。归零说明状态退回了内存变量，属回归，请提 issue |
| 改了代码但行为没变 | 忘了点刷新（⟳）。watch 只重新 bundle，浏览器侧不会自动重载 |
| 关掉浏览器重开，popup 里**还是有一堆资源** | **正常**。会话存储确实被清空了（2026-08-09 用 `chrome.storage.session` 手动放标记实测：重启后读回空对象），但 Edge 会恢复标签页并**自动重新加载页面**，一加载就又采了一遍。要确认是不是残留，看条数会不会**比重启前少** —— 我们没有任何会让条数减少的代码路径（50 条以内不淘汰），所以变少就一定是清过又重采 |
| 同一页刷新几次，条数越来越多 | **也是正常的**。HLS 的自适应码率每次可能选不同档的清单，那是**真实不同的 URL**；而我们**刻意不在页面导航时清桶**（单页应用切视频不触发导航，清了反而丢数据）。想归零就把嗅探开关关掉再打开 |
| 刚重启浏览器，恢复的页面**只采到很少几条** | 已知取舍。service worker 冷启动时要先异步读一次开关状态，**在读回来之前一律按「关」处理**（宁可漏嗅，不可在你没开时监听），这段窗口里最早的几个请求会漏掉。强制刷新一次本页即可补齐 |
| 资源比预期少 / 第二次打开同一页反而更少 | **已知边界**（2026-08-09 实测）：**浏览器缓存命中的请求不会产生响应头事件**，而嗅探全靠响应头 —— 走缓存的那部分就检测不到。实测同一页第一次采到 4 条、关掉标签页重开只剩 2 条。popup 的「**强制刷新本页**」按钮就是为此存在的（它绕过缓存，不是普通刷新），或自己按 Ctrl+F5。**我们不会为此再加一个监听器**：那只会让同一资源两次入列，换不来准确性 |

## 扩展 ID

```
joomlppocobhkaeinpcmkkbphnjmjiei
```

由 `extension/manifest.json` 里固定的 `key` 字段派生，因此**换目录、换机器都不变**（构建脚本每次构建都会打印它）。DownLord 侧对 `Origin` **只校 `chrome-extension://` 前缀、不做 ID 白名单**（理由见下文安全边界 —— 本机程序能任意伪造 `Origin`，白名单挡不住它，只会变成登记负担）。

## 权限（只按表增，可核验）

| 权限 | 哪个 Task 加的 | 为什么 |
|---|---|---|
| `storage` | Task 2 | 存唤醒计数、存配对码与最近一次握手结果 |
| `host_permissions: ["http://127.0.0.1/*"]` | **Task 3** | 让 sw 能直接 POST 到本机通道而**不受 CORS 约束** |
| `downloads` | **Task 4** | 收下载事件、在 DownLord 受理后取消浏览器原生下载 |
| `webRequest`（观察型） | **Task 5** | 读响应头的 `Content-Type` / `Content-Length` 来识别页面上的媒体资源 |
| `host_permissions: ["<all_urls>"]` | **Task 5（表外新增）** | 观察型 `webRequest` 要对目标 URL 持有 host 权限，够不着就什么都嗅不到 |
| `cookies` | **Task 6** | 在浏览器**内部**读被点名那一个站点的 Cookie —— Chrome / Edge 运行时外部程序读不到它们的 Cookie 数据库（App-Bound Encryption），这正是「从扩展获取 Cookie」这一档存在的全部理由 |

### 安装时那句吓人的提示 —— 如实解释

安装时 Edge 会提示本扩展可「**读取您在所有网站上的数据**」。这是 `webRequest` 观察权限的标准提示。

- 本扩展**不注入页面脚本、不读取页面内容** —— manifest 里**没有** `content_scripts`、**没有** `scripting` 权限（产物断言 A5″ 每次构建都在查）；
- 它只看网络请求的**地址与响应头**，用来判断「这是不是一个媒体资源」；
- **嗅探默认关闭**，由你在 popup 里自己打开；
- 嗅探结果只留在**浏览器内存**里，关标签页即清该页、**浏览器进程真正退出后全清**，不落盘、不落库、不上报任何远端；
- **没被你点选的资源从不离开浏览器** —— DownLord 只在你点了某一条时才收到那一条。

⚠️ **「关浏览器即清」这句话的准确边界**（2026-08-09 实测得出，写在这里免得被读成更强的承诺）：

- 清的是**存储**，不是你眼睛看到的数字。Edge 重启后会**恢复上次的标签页并自动重新加载**，页面一加载就又被采了一遍 —— 所以重开浏览器后 popup 里通常**不是零**，那是新采的，不是残留；
- 「浏览器进程真正退出」是前提。`edge://settings/system` 里的「**启动加速**」和「**关闭 Microsoft Edge 后继续运行后台扩展和应用**」会让 `msedge.exe` 关窗后仍常驻，此时浏览器会话根本没结束，内存里的东西自然也不会清。要确认可在终端跑 `tasklist | grep -i msedge`；
- 想立刻清干净、且不依赖任何浏览器行为：**把 popup 里的嗅探开关关掉**，那会当场删掉全部标签页的采集结果（关掉后那一行会显示「已关闭 · 0 条」—— 如果显示的不是 0，说明清空失败，请提 issue）。

⚠️ **`host_permissions` 的如实表述**：MV3 的 match pattern **语法上不支持端口**，所以 `http://127.0.0.1/*` 那条实际是**回环全端口授权**，**不能说成「只授权 52330」**。
Task 3 **没有**加 `alarms` —— 握手是事件驱动的，不需要定时器（代价就是上文「待活动」那一态分不清挂了还是闲着）。
产物断言用**全等**而非 `includes` 检查这两个字段：悄悄多要一个权限，`npm test` 当场变红。

### 那句 Cookie 提示 —— 同样如实解释（v0.4 Task 6 起）

安装时 Edge 还会提示本扩展可「**读取和更改您在所有网站上的 Cookie**」。这是 `cookies` 权限的标准提示。

- 我们**只在你点击下载时、只读被点名那一个站点的 Cookie，从不写入、从不删除、从不后台收集**。时序是：你在 popup 点「用 DownLord 下载此页视频」→ DownLord 在应答里**点名**要哪些精确 host 的 Cookie（`needCookieFor`，**最多 2 个**）→ 扩展才调 `chrome.cookies.getAll`；
- **点名只能落在这次请求自己携带过的 URL 上**（`cookies/cookiePick.ts` 的 `pickCookieUrls`）—— 就算应答被伪造成 `needCookieFor: ["bank.com"]`，扩展手里也没有那个域的候选 URL，`getAll` **压根不会被调用**。这是**结构约束，不是策略**；
- **没有定时器、没有预取** —— 扩展**没有** `alarms` 权限，`extension/src/cookies/` 里一个 `setInterval` 都没有（红线 R9 的判据 A-4 就在扫这个）；
- 扩展这一侧**不存 Cookie**：读到就发给本机的 DownLord。`extension/src/cookies/` 全目录**一条 `storage.*` 都没有、一条 `console.*` 都没有**（可自己 grep 核验）—— 后者比「不记域名」更严，理由是扩展的 console **任何装了它的人都能在 sw DevTools 里翻**。

⚠️ **不许把这段读成「所以其实没风险」**：声明宽就是宽 —— 那句提示里的「**更改**」和「**所有网站**」我们都用不到，但浏览器是按声明授权的。上面那些对冲（只在你点下载时读、只读被点名的那一个 host、不存不打日志）**降低的是影响，取消不了权限**。DownLord 那一侧拿到 Cookie 之后怎么处置（只活在内存 / 临时文件用完即删 / 连域名都不写日志），记在 [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) §7.6。

⚠️ **反过来也要说全 —— 这一档的能力边界比听起来窄**：因为「点名」只能发生在**扩展先来说话**的那次应答里，所以它**只对扩展点过名的域生效**。你**不经扩展、直接把链接粘进 DownLord**，而此前从没经扩展借过这个站，那么 DownLord **拿不到这个站的 Cookie**，下载会如实报「需要登录」。这是通道**不做反向推送**的必然结果（见「已知边界」第 ④ 条），**任何设计都堵不上**，所以这里如实写明而不含糊过去。

### 转交下载时带哪些请求头

只带 **`Referer`** 与 **`User-Agent`** 两个（白名单，取自主仓共享常量）。**不带 Cookie** —— 需要登录态时走上面那一档，而不是把 Cookie 混在头里发。

## 安全边界（如实写，不做承诺）

通道是 **HTTP over 回环**，鉴权靠三件事分工（**不是三倍安全，它们挡的是不同的人、不叠加**）：

1. **配对码走请求头** `X-DownLord-Token`（不放 query —— query 会进各种 URL 记录）。这是**唯一挡本机程序的一闸**；
2. **跨源预检一律不放行** —— DownLord 对 `OPTIONS` 不回任何跨源放行头，于是**浏览器自己**在把网页 JS 的请求发出去之前就拒掉它。挡的是**网页上的 JS**，不是本机程序（本机程序压根不做预检）；
3. **`Origin` 前缀校验** —— 纵深而非主闸：网页 JS 无法伪造自己的 `Origin`，但**本机任意程序可以随便伪造**。

**它挡不住什么（逐条如实）**：

- ① **能以你的用户身份读文件的程序**能从 `%APPDATA%\DownLord\config\extensionChannel.json` 直接拿到配对码，此后可完整冒充本扩展；
- ② **扩展这一侧的配对码明文存在浏览器 profile 目录里**，同样能被翻出来（换成 `storage.session` 可以不落盘，但那样每次重启浏览器都要重新配对）；
- ③ **没有做恒定时间比较** —— 在上面这个威胁模型下它没有意义，如实写明而不假装加固；
- ④ **是 HTTP 不是 HTTPS** —— 本地自签证书浏览器不认。回环流量**不出网卡**，但**同机进程仍可抓**；
- ⑤ **端口被别的程序占着时，popup 那次「保存并连接」会把配对码发给那个程序**。DownLord 侧会如实显示「端口被占用，通道未启动」让你看得见异常，但**发出去就是发出去了** —— 遇到第四种排障提示后，建议回 DownLord 点一次「重新生成」；
- ⑥ **同一个配对码允许多个浏览器实例共用**，因此 DownLord 只记「最近一次握手」，**分不清是哪个浏览器连的**（v1.0 实测范围为 Edge + Chrome）；
- ⑦ **失败限速只作用于失败请求** —— 刻意如此：否则本机任意程序可以靠刷失败把**合法扩展一起挡死**。

所以：**不宣称「绝对安全」、不宣称「加密传输」、不宣称「保证不被其它程序访问」**。真正在挡本机攻击者的**只有配对码这一件事**；第 2、3 条挡的是浏览器里的网页 JS。

## 已知边界（如实写，不隐瞒）

1. **DownLord 升级会重写 `resources/` 目录** → 走路径 A 装的 unpacked 扩展**可能需要在 `edge://extensions/` 手动重新加载一次**。这是 unpacked 分发形式的固有属性，**不是缺陷**。
2. **不打 `.crx`、不上商店**（v0.4 范围内）。因此**没有自动更新通道** —— 扩展随 DownLord 一起更新。
3. **将来若签 `.crx`，会换新 key、换新扩展 ID**，届时已配对的用户需要**重新配对**。
4. **通道不做反向推送**（无 WebSocket / SSE）—— MV3 的 service worker 空闲即被销毁，长连接不可靠。所以是扩展**主动请求**、DownLord 应答；DownLord 想让扩展知道点什么，只能等扩展下次来问。
