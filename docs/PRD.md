# DownLord — 产品需求文档(PRD)

> 本文档是 DownLord 的**产品层**事实来源:产品定位、目标用户、痛点、用户旅程、MVP 范围与验收。
> 技术实现与约束见 [ARCHITECTURE.md](./ARCHITECTURE.md);视觉与交互规范见 [DESIGN.md](./DESIGN.md);各版本已交付内容见根 [CHANGELOG.md](../CHANGELOG.md)。

---

# 1. 产品定位

一句话:

> “Windows 端的全能下载器——多线程加速、视频解析、磁力 BT、网页嗅探、浏览器接管,一个工具搞定。”

DownLord **是**:

- Windows 桌面下载器
- 多线程分段加速下载工具(IDM 式)
- 视频解析下载器(站在 yt-dlp 肩上,支持上千站点)
- (后续)BT / 磁力下载、网页资源嗅探、浏览器下载接管的统一入口

DownLord **不是**(差异化边界):

- 翻墙工具(不提供节点,仅对接用户已有的系统代理 / Clash)
- 云端 / 在线下载服务,也不是迅雷式的 P2SP 离线下载服务器
- 盗版资源搜索 / 聚合平台(工具中立,不内置资源站)
- 浏览器 / 播放器 / 账号产品

> **愿景是「全能」,但分阶段落地**:MVP(v0.1)先做「多线程下载 + 视频解析」两件最高频的事,BT / 嗅探 / 接管按 Phase 2–4 逐步补齐(见 §9)。

---

# 2. 目标用户

- 有高频下载需求、希望多线程加速(而非浏览器原生慢速下载)的用户
- 想下载各视频站点(抖音 / B站 / YouTube 等)内容的用户
- 受够了「装猫抓 + IDM + 迅雷 + 视频下载器」四件套、想要一个工具搞定的用户
- 进阶用户(已用 Clash 等代理),希望下墙外站点时无需反复开全局 VPN

---

# 3. 用户痛点

> 由「目标用户 + 核心理念」提炼,作为功能取舍依据。

- **工具分散**:嗅探、加速、视频、BT 要装四个不同软件,各管一摊、体验割裂。
- **原生下载弱**:浏览器原生下载单线程慢、不能分段加速、断了往往要重来。
- **视频下载难**:视频站点下载需专门工具,且站点频繁改版导致工具失效。
- **墙外站点麻烦**:下载墙外站点要反复开 / 关全局 VPN,影响整机其他网络。
- **全能即臃肿**:现有「全能」工具要么臃肿卡顿,要么界面廉价、体验粗糙。

# 4. 核心设计理念(产品原则)

> 这些 First 是产品级取舍准则。其技术落地约束见 [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 4.1 Integration First(整合优先)

一个工具覆盖嗅探 / 加速 / 视频 / BT,替代多件套。统一的任务列表、统一的添加入口、统一的设置——这是 DownLord 最大的差异化。

## 4.2 Engine Reuse First(引擎复用优先)

站在成熟开源引擎(aria2 / yt-dlp / ffmpeg)肩上,**不重造下载 / 解析协议**。产品价值在「整合 + 体验 + 界面」,不在底层轮子。

## 4.3 Quality First(质量优先)

稳定、可维护、界面专业舒服不廉价。布局守正(沿用成熟下载器范式),气质与整合度出奇。

## 4.4 Honest First(诚实优先)

不承诺做不到的事。**不提供翻墙能力**(物理上需要用户自带代理节点);下载内容的版权 / 平台 ToS 边界如实告知,不做虚假安全 / 合规承诺。

# 5. 核心用户旅程

1. **添加**:粘贴链接 / 拖入 → 自动识别「直链」vs「视频」,可手动切换。
2. **(视频)选择**:解析出可选清晰度 / 格式,选一个;或勾「仅音频转 MP3」;播放列表可批量。
3. **下载**:多线程分段加速、断点续传;按**文件类别**自动归类到对应文件夹。
4. **管理**:任务列表按状态(下载中 / 已完成 / 失败)或文件类型筛选;暂停 / 继续 / 重试。
5. **(墙外站)代理**:下载 / 解析流量走已配置的系统代理 / Clash,**无需单独开全局 VPN**;国内站由代理规则直连、不费境外流量。
6. **完成**:打开文件 / 打开所在文件夹;完整历史可查(SQLite)。

# 7. 功能黑名单(明确不做)

> 跨版本长期红线。

- 内置 VPN / 翻墙节点 / 墙外中转服务(合规红线 + 物理约束:工具变不出网络路径)
- 云同步 / 跨设备同步 / 账号体系
- 盗版资源搜索 / 资源聚合站 / 内置片源
- 专门破解会员 / 绕过付费墙的功能(Cookie 登录用的是用户自己的登录态,不在此列)
- 迅雷式 P2SP 私有加速网络 / 离线下载服务器(无商业基础设施,不可复制)
- 自行绕过浏览器 App-Bound Encryption 读取 Cookie(需调用 Chrome elevation service 或进程注入,与安全红线冲突且会被杀软报毒;登录态只经用户自己的浏览器扩展点名给予)

# 8. 验收标准(产品层)

> 产品级通用验收原则。

- 能多线程加速下载直链,断点续传可靠(中断 / 重启后续传不丢)。
- 能解析并下载主流视频站(抖音 / B站 / YouTube 等),含选清晰度、音频提取、批量。
- 按文件类别正确归类保存到对应目录。
- 代理三档均正确工作,墙外站经代理可下,国内站不被无谓代理拖慢。
- 界面专业舒服、浅 / 深色一致、不廉价。
- 错误有可读中文提示、失败可重试、任务不丢失。
- 工具行为诚实合规,不做虚假翻墙 / 安全承诺。

# 9. 版本方向(Roadmap)

> 方向性规划;各版本实际交付见根 [CHANGELOG.md](../CHANGELOG.md)。

- **v0.1(MVP · ✅ 已交付)**:Phase 0 下载内核 + 基础界面;Phase 1 视频解析下载。
- **v0.2(能力增强 + 体验完善 + 质量修复 + 更新体系 · ✅ 已交付 2026-07-14)**:视频 Cookie 登录 + 字幕、下载限速 + aria2c 分片加速、检测重复下载(修 0B 假完成)、剪贴板监控、历史搜索 / 统计 + 复制链接、yt-dlp 独立热更新 + 应用本体自更新(electron-updater + GitHub Releases);未签名如实声明(§4.4,代码签名继续留后续)。
- **v0.3(Phase 2:BT / 磁力下载 + 质量优化收尾 · ✅ 已交付 2026-07-28)**:复用 aria2 **原生** BT / magnet 能力(不重造协议)——magnet / `.torrent` 识别与添加、**元数据阶段**、**多文件种子文件选择**(单文件豁免直下)、**做种(默认下载完即停、可选开启 + 随时停止做种)**、**富进度**(节点数 / 上行速度 / 分享率,全为运行时不落库)、设置页「BT · 磁力」分组 + 左导航 BT 入口激活;新 `kind='torrent'` 经 schema **v3 迁移**重建 `tasks` 源数据表(先备份 + 单事务 + 零丢失断言)。质量优化收编四项(按 protocol 精细化挂 aria2c,回退不退化 / 单任务限速「跟随全局」第三态 / 查重 `source` 索引,migration v4 只加索引零数据触碰 / 「最高 / 封顶」清晰度归一)+ 2026-07-11 审计高价值项 4 项;推迟 8 项如实记录在案。**诚实缺口如实告知**:BT 入站可达性受 NAT / 运营商限制(做种上传可能长期为 0,UPnP 未做)、内置 tracker 为 2026-07-25 静态快照(自动更新未做)。**两条均已在 v0.4 Task 1 还账**——tracker 表已实现应用内自动更新,入站可达改为自检(UPnP 明确不做),见下方 v0.4 条。
- **v0.2.1 / 内嵌浏览器登录取 Cookie(~~往后推~~ · 🚫 已取消)**:~~应用内嵌浏览器登录 → 自动取 Cookie(根治 Chrome/Edge App-Bound Encryption 对外部读 cookie 的限制),轻登录作 Phase 3/4 浏览器接管的前置。**开发期先用 Firefox cookie**(实测可下 B 站),该方案留 v0.3 之后按需立项。~~
  > **已由 v0.4 的浏览器扩展方案落地(2026-08-19),内嵌浏览器不再做。** 扩展跑在用户自己的浏览器内部,本就绕开了 ABE,用户也无需在 DownLord 里重新登录一次——整个内嵌浏览器子系统因此不必再建。原文保留追溯。
- **v0.4(浏览器扩展接管 · Phase 3 + Phase 4 合并 · ✅ 已交付 2026-08-21)**:**一个浏览器扩展 + DownLord 侧本地通道**,一次落地原 Phase 3 与 Phase 4 的核心价值。六个 Task 的实际交付:
  - **Task 1 — BT 连通性还债**:tracker 表**应用内自动更新**(添加 BT 任务时按需拉取,内置表只在拉取失败时兜底,并对已在跑的任务追补);**入站可达自检**(纯本地检测、如实呈现)。
    > **据实订正(不是改主意,是把规划期的待定项按 2026-07-29 的决议写实)**:原文写的是「UPnP **先实测 CGNAT 再定**」,现结论为——**不做 UPnP;改为入站可达自检,只检测与如实呈现、不承诺打通 NAT**。理由:校园网的出口设备不归用户管、CGNAT 家宽同样无效,而有公网 IPv6 时 UPnP 又用不着(它只管 IPv4)。**现行处置：UPnP / NAT-PMP 本体不做**，保留已交付的入站自检，不再指定后续版本。
  - **Task 2 — 扩展工程地基**:MV3 扩展作为**第二个可分发工件**独立构建(esbuild),版本由 `package.json` 单一真源注入,产物断言 + 独立 typecheck 纳入门禁。
  - **Task 3 — 本地通道 + 一次性配对**:只绑 `127.0.0.1` 的 HTTP 通路,**三闸分层**鉴权(配对码请求头 / 拒绝一切跨源预检 / `Origin` 前缀校验);**默认关闭**,设置页新增「浏览器扩展」分组。
  - **Task 4 — 下载接管**:浏览器里点下载 → 取消原生下载 → 交 DownLord,**弹独立确认框、永不静默**;命中重复时在同一窗口内四选一;支持**临时暂停接管**(真源在主进程)。
  - **Task 5 — 网页资源嗅探**:识别页面上的 m3u8 / mp4 等媒体资源、分片归入其清单条目,**popup 是唯一呈现处**(结果不上行、不落库),一键转交 DownLord;嗅探**默认关闭**。
  - **Task 6 — 扩展取 Cookie**:视频 Cookie 来源新增第四档「从扩展获取」——由 **DownLord 点名、扩展给予**该站登录态,**只活在内存、用完即删**。⚠️ 该档**只对扩展点过名的域生效**:用户绕开扩展、直接把链接粘进 DownLord 且此前从未借过该站时取不到,这是通道不做反向推送的必然,**任何设计都堵不上**,故 UI 与文档如实交代。
  - **交付物**:`downlord-0.4.0-setup.exe` + `downlord-extension-0.4.0.zip`;**零 schema 迁移**。
  - **范围边界（现行口径）**：Edge 与 Chrome 均已实测通过、同为承诺范围；**Firefox 扩展本版不做**，不影响 Firefox 直接读取 Cookie 的路径。扩展仍**不上任何扩展商店**，需在开发者模式手动加载；这是现行支持说明，不追改当时实测记录。
  - **仍然如实告知的缺口**:应用**未做代码签名**(安装时 Windows 提示「未知发布者」)· 应用**自更新链路从未真机闭环**(`publish.owner` / `publish.repo` 当时仍为占位符,刻意不预填)· 扩展**权限声明比实际行为宽**(浏览器提示「读取您在所有网站上的数据」,实际只看请求地址与响应头)· BT **入站可达只检测不承诺**。

  > **⚠️ 本条推翻了原 Phase 3 / Phase 4 的设定(2026-07-28 拍板,v0.4 已按此交付)**。原文见下方「历史设定」小节,**保留追溯、不删改**。推翻理由三条,交付后逐条复核仍然成立:① **内嵌浏览器只能看见 DownLord 自己那个窗口里的流量**——用户在自己的 Edge 里浏览时它一无所知,做不出 IDM 式的后台接管(操作系统级进程隔离;除非 MITM 抓包 + 装根证书,属安全灾难,IDM 亦不如此);② **一个扩展同时解决了三件事**(downloads / webRequest / cookies)——v0.4 的 Task 4 / 5 / 6 即此三件,而内嵌浏览器只解决其中一件的一部分;③ **扩展取 Cookie 因此更优**——扩展跑在浏览器内部,**天然绕开 Chrome/Edge 的 App-Bound Encryption**(ABE 防的是外部进程),用户在浏览器里本就是登录态,无需在 DownLord 内重新登录,**整个内嵌浏览器子系统未建、也不会再建**。

- **原候选池的现行处置（各事项已分别裁决，不是待排期清单）**：
  > 原候选池的组织性标题不构成单项裁决。以下各项已分别裁决，不再以“规划期待拍板”维持失效承诺，也不为这些事项新指定版本。

  **逐项边界（保留成因，不恢复未来排期）**：
  - **UPnP / NAT-PMP 本体不做** —— 已交付的是入站可达自检。校园网出口不归用户管、CGNAT 家宽无效，UPnP 又只处理 IPv4；不把自检写成打通能力。
  - **多浏览器 / 多实例连接区分不做** —— 当前仅记最近一次握手，不提供各浏览器同时连接的独立身份视图。Edge / Chrome 同为承诺范围不等于这项区分能力已交付，也不再以等待 Firefox 为排期理由。
  - **收窄宽 host 权限属于新增能力,本版不做** —— 动态授权与全局观察型 `webRequest` 监听器的组合未实测，本版不修改权限；如实告知现有宽声明及风险。扩展仍开发者模式加载、ZIP 分发，不承诺商店上架或与 Firefox 同期处理。
  - **Firefox 扩展本版不做** —— 命名空间、MV3 后台形态和正式版签名分发存在差异；预留适配口不等于可用。此结论不否定 Firefox 外部直接读取 Cookie 的既有路径。
  **待评估、落点未定**:质量优化的推迟项、接管与嗅探的深化(视真机反馈)。**未分配到任何版本。**

- **待用户亲自执行 / 发布前置(不是版本候选,不进路线图)**:
  > 这两条不是「哪个版本做」,而是「**用户什么时候真去发布**」——把它们塞进版本路线图,会让人误以为在等某个版本。
  - **发布闭环** —— `electron-builder.yml` 的 `publish.owner` / `publish.repo` 仍是占位符,本项目尚未建远程仓库、未发过 Release,因此「检查更新 → 下载 → 重启安装」从未真机跑通。**刻意不预填**:填了却没有对应 Release,只会把诚实的占位换成会失败的真配置。建仓与发布属对外动作,由用户亲自执行。
  - **代码签名** —— 决策自 v0.2 起未变:**维持未签名**,README 如实说明「安装时 Windows 可能提示未知发布者」。本项目可能作为开源仓库发布、不一定需要证书;何时买证书由用户决定(且**签名后能否消除全部告警不作保证**)。

### 历史设定(已于 2026-07-28 推翻,保留追溯)

> 以下为 v0.4 规划前的原 Roadmap 表述。**现已由上方 v0.4 条目取代**,列此仅供追溯决策演变,**不再作为执行依据**。

- ~~**Phase 3(网页嗅探 · v0.4+)**:内嵌浏览器(Electron 即 Chromium)监听网络请求,识别 m3u8 / mp4 等媒体一键下载(猫抓式)。~~
- ~~**Phase 4(浏览器接管)**:浏览器扩展 + native messaging host,拦截下载转交 DownLord 加速(IDM 式)。~~

> 订正说明:嗅探与接管**合并由同一个浏览器扩展落地**;通信不走 native messaging 而走**本地 HTTP + token**(绑 `127.0.0.1`,与既有 aria2 RPC + `--rpc-secret` 同构)——理由是 native messaging 需写注册表、需固定扩展 ID(旁加载扩展 ID 会变)、且浏览器 spawn 的 host 是短命进程仍需再转发一层,而本地 HTTP 无这些负担且易测。

- **增强项**:剪贴板监控、限速、Cookie 登录下载、字幕、完整历史搜索 / 统计等 **✅ 已在 v0.2 交付**;**BT / 磁力(Phase 2)✅ 已在 v0.3 交付**(遗留的 UPnP 与 tracker 热更新已在 v0.4 Task 1 处置);代码签名(消除 SmartScreen「未知发布者」)**继续留后续**(项目可能作为开源仓库发布、不一定需证书;v0.2 已做未签名诚实声明 + 环境变量预留口,v0.3 收口维持该决策不变)。
